# Workly — 5,000-Visitor Readiness Report
**August 27, 2026**

This report covers the three things you asked for: live persona-based testing across job-seeker types and cities, a fresh security audit specifically for 5,000-visitor scale, and a thorough walkthrough of payment-tier options with a recommendation.

One piece of context up front, because it shapes all three sections: since the last audit, another work stream has been committing directly to the live repo — 7 new commits, including one titled *"implement daily AI discovery limits and lay UI infrastructure for unlimited tier upsells."* That commit already built half of a paywall (a hard 3-discoveries-per-24-hours cap and an `isPro` flag on every user) without the other half (no way for `isPro` to ever become `true`, no pricing page, no payment processor). I found and fixed two bugs this introduced — one was serious — and folded the existing scaffolding into the payment-tier recommendation below rather than proposing something disconnected from what's already half-built.

## Part 1 — Persona testing: is it ready to use?

I ran the app like six different real users, end to end, in a fresh copy of the site with a real (local) database: a university student in Boston (Student Mode), a busker/street musician in Austin (Gig/Freelance Mode), a barista in Manchester working part-time, a rideshare driver in Toronto (Gig/Freelance Mode), a waiter in Sydney (no special mode), and a marketing coordinator in Chicago (the baseline "normal" full-time job seeker). Each one signed up for real, verified their email, completed onboarding with realistic answers, built out a career profile, ran job discovery, used the dream-job analyzer, and checked their applications and career-path pages.

**Result: zero crashes, zero 500 errors, zero stack traces reaching the screen, and zero cross-account data leakage**, across all six accounts and roughly 40 actions. Every score the app showed was honestly caveated rather than invented — when a profile didn't have enough information, the app said so plainly ("Not enough information... this is your Candidate Fit for this role, not a hiring probability") instead of showing a fabricated number. That's the "show a real score or honestly refuse" design principle from earlier work holding up under live testing, not just in code review.

Two small, real issues came out of this testing pass, both cosmetic rather than functional. First, when Gig/Freelance Mode is turned on, the Career Profile form still shows corporate placeholder text ("Senior Product Designer," "Acme Inc.") instead of gig-relevant examples — a busker or driver filling out that form sees copy written for someone else's job search. Second, Student Mode skips the resume-review step and drops the new user straight onto the student hub, which is a real behavioral quirk worth knowing about even though nothing breaks.

One thing I could **not** verify: whether location actually changes which jobs show up. Every real job-board API call from this sandbox came back `HTTP 403` — the sandbox's network is blocked from reaching those APIs, not a bug in the app. What I *could* confirm is that each user's city was saved correctly and never crossed between accounts, and the app handled every one of those 18 failed API calls gracefully (a clear "no new listings" message and an "Error" badge on the source, never a crash). Before you'd want to fully trust the location-matching behavior for real users, someone should re-run job discovery from a network that can actually reach those job boards — Vercel's production environment should be fine here since this 403 is specific to this sandbox, not a Workly problem, but it's worth a real confirmation rather than an assumption.

I also specifically re-tested the daily-discovery-limit feature the other work stream just added, including a bug I found and fixed in it (more in Part 2) — running discovery a 4th time in the same 24 hours now correctly shows the user a visible message telling them they've hit their limit, confirmed in the actual rendered browser, not just in the code.

**Verdict: functionally ready for real traffic.** The only open item is the location-matching confirmation above, which depends on network access this sandbox doesn't have — not something in the app itself.

## Part 2 — Security re-audit for 5,000 visitors

This is a different question from the "10,000 users" audit two turns ago, which was mostly about registered-user data volume. Five thousand *visitors* is about load and abuse surface from people who may never sign up: how the site behaves under concurrent anonymous traffic, whether rate limits hold up on serverless, and whether the database can take the connection pressure.

### Confirmed still fixed
Both critical issues from the last audit are still intact after the 7 new commits: the unauthenticated `/api/fix-db` endpoint is still deleted, and the cron job-alert endpoint still fails closed (refuses every request) in production if `CRON_SECRET` isn't set, instead of falling back to a guessable comparison.

### New critical issue found and fixed: broken job-alert cron
The same commit that added the discovery-limit feature also added two new columns to the `User` model in the schema — `isPro` and `lastAlertSentAt` — and wired the weekly job-alert cron job to filter and update on them. Nobody wrote the database migration for those columns. I confirmed this directly: running the cron job's actual query against the database throws `column "isPro" does not exist`. That means the job-alert emails — the feature that's supposed to bring lapsed users back weekly — have been silently broken since that commit landed, and this would fail identically against your real production database, since it's a live column reference with no migration behind it anywhere in the codebase.

I wrote and applied an additive migration (`ADD COLUMN IF NOT EXISTS`, matching the safe pattern used everywhere else in this project) that adds both columns with safe defaults, ran it against the local database, and confirmed the cron query now works. This is safe to deploy — it only adds nullable/defaulted columns and touches nothing existing.

### New issue found and fixed: invisible upgrade prompt
When a user hits the new 3-discoveries-per-24-hours limit, the code was already tracking that state (`upgradeRequired`) but never rendered anything for it — the "Discover" button would just stop spinning with no explanation at all, which reads as the button being broken rather than a limit being reached. I added the missing message. My testing agent confirmed live in the browser that hitting the limit now shows a clear "Daily discovery limit reached... resets in 24 hours" message.

### Issue found and fixed: a security test had gone blind
The automated test that checks every page for proper "does this record belong to the signed-in user" protection was reporting two pages (`applications/[id]/challenge` and `applications/[id]/interview`) as unguarded. I traced this down and confirmed those two pages are **actually secure** — they use a different, equally valid pattern than the rest of the app (passing the signed-in user's ID straight into a database lookup that already filters `WHERE id = $1 AND userId = $2`, so a mismatched owner just comes back as "not found," rather than fetching the record first and comparing afterward). The test's pattern-matching just didn't recognize that second pattern. I fixed the test to recognize both. This wasn't a live vulnerability, but it's worth flagging on its own: **a security test that reports false positives is a test people learn to ignore, and the next time it fires it might be a real hole.** Worth keeping an eye on whenever a new page pattern shows up.

### One open question I can't answer from here
The database connection pool is configured with `max: 3` connections per instance, with a comment noting it should route through a connection pooler (Supabase's pooler, or PgBouncer) rather than a direct connection when deployed. That's the right design *if* the production `DATABASE_URL` actually points at a pooled connection string — I can only see the local `.env` in this sandbox, not your real Vercel environment variables, so I can't confirm which one production is using. This matters specifically at 5,000-visitor scale: Vercel can spin up many serverless function instances under concurrent load, and if each one opens a direct (non-pooled) connection, you can hit Postgres's connection limit and start seeing "too many connections" errors under a traffic spike, even though the app code itself is fine. Worth a two-minute check in your Vercel dashboard: does `DATABASE_URL` (or whichever variable is actually loaded) use the pooler port, not the direct one.

### What's already solid
Every sensitive endpoint I checked — signup, login, password reset, email verification, resend — has real rate limiting, and it's implemented against Postgres rather than in-memory, which is the right call: in-memory rate limits reset on every cold serverless instance and would effectively not work at real scale, but a database-backed check works correctly no matter how many instances Vercel spins up. Of the 40-plus API routes in the app, only two skip an explicit auth check, and both are supposed to (starting the Google sign-in flow, and clearing a stale session cookie) — neither leaks anything. Security headers are properly set on every response: a real Content-Security-Policy with a nonce, HSTS, X-Frame-Options, and the rest. Database errors are translated into safe, generic messages before reaching users rather than raw Postgres errors. TypeScript compiles clean, the production build succeeds, and all 256 automated tests pass, including the isolation test after my fix.

**Verdict: ready for 5,000 visitors**, with the one caveat above (confirm the pooled connection string in Vercel) being the only item I'd want resolved before a real traffic spike rather than after one.

## Part 3 — Payment tiers, thoroughly, with a recommendation

### What's already half-built
Before getting into options, it's worth being direct about where the code already stands: there's a hard usage limit (3 AI discovery runs per user per rolling 24 hours) that applies to *everyone* right now, a `isPro` flag on every user account that's always `false` because nothing anywhere ever sets it to `true`, and an "upgrade" message that — until today — pointed at nothing. There's no pricing page, no Stripe integration, no checkout flow, and no way for a real payment to ever reach that `isPro` flag. In other words: the *metering* half of a freemium paywall exists; the *payment* half doesn't. That's actually a good position to be in — the hardest, most failure-prone part of a paywall (deciding what to gate and building the gate itself, without breaking the free experience) is already done and tested. What's missing is comparatively mechanical: a pricing page, a Stripe integration, and one line of code that flips `isPro` to `true` on successful payment.

### The tier options, and their tradeoffs

**Option A — Simple monthly/annual subscription (classic SaaS).** One paid tier, say $12–15/month or $99–120/year, that removes the daily discovery cap, unlocks the dream-job analyzer and AI-assisted CV feedback without limits, and adds the job-alert emails (once the cron bug above is fixed and something eventually sets `isPro=true`). This is the standard path and the one nearly every competitor (Teal, Huntr) uses, at $26–40/month effective pricing once you account for their annual discounts — so there's real room to charge more than the range above once you have usage data to justify it. The build is moderate: Stripe Checkout, a webhook that flips `isPro`, and a customer portal for cancellation. Recurring revenue compounds, but subscription products in job-search specifically suffer from "I got the job, I'm cancelling" churn, which is structurally higher than most SaaS categories — annual billing is the standard fix, since it cuts effective churn 60–80% compared to monthly.

**Option B — One-time credit packs.** Sell blocks of AI discovery runs or dream-job analyses (say, 20 runs for $9, or 50 for $19) instead of a subscription. This maps almost perfectly onto the limit that's already built — the 3-per-24h cap becomes "3 free per day, or spend a credit to skip the wait," which is a much smaller code change than building a full subscription tier. No recurring billing relationship to maintain, no churn to fight, and it's psychologically easier for a first-time payer to say yes to $9 once than $15/month forever. The tradeoff is revenue ceiling: without a recurring hook, monthly revenue depends entirely on new credit-pack sales each month rather than compounding.

**Option C — One-time lifetime unlock.** A single payment (e.g. $59–79) removes all limits permanently. This converts well precisely *because* job searching is time-bound — most users only need the tool intensively for 2–4 months, so "pay once, never again" is a genuinely more honest pitch than a subscription for a temporary need, and it's the easiest possible thing to build on top of what exists (one Stripe Checkout session, one webhook, one `isPro=true`, done — no recurring billing infrastructure at all). The obvious downside is no recurring revenue: every dollar is one-time, so growth depends entirely on new-user volume rather than a compounding subscriber base.

**Option D — Hybrid: free tier with the existing cap, one-time "unlock a job search" pass, and a recurring "career coach" tier.** The one-time pass ($39–49) removes limits for, say, 90 days — matching how people actually use a job-search tool — while a separate, higher-priced recurring tier ($20–25/month) adds things that only make sense as an ongoing relationship: 1:1 coaching call credits, priority AI processing, or continuous job-alert monitoring even after someone's stopped actively searching (for career-watching, not just active search). This captures both buyer types — the person who wants to pay once and be done, and the person who wants an ongoing service — but it's the most code to build, since it's really two payment products instead of one.

### My recommendation

Given what's already in the codebase, **start with Option C (one-time lifetime unlock) as the very first thing you ship, then layer Option A (subscription) on top once you have real conversion data.**

The reasoning: the existing `isPro` flag and discovery cap don't care *how* someone became a Pro user — a one-time Stripe Checkout that flips one boolean is the single smallest change that turns the already-built metering system into working revenue, likely a day or two of focused work rather than a week. It also matches the honest framing you'll want anyway: telling a stressed job-seeker "pay once, use it until you're hired" is a more trustworthy pitch than asking them to commit to a subscription during what's often a financially tight period, and it sidesteps the "cancel the moment I get the job" churn problem entirely, since there's nothing to cancel. Once you have even a few weeks of real conversion and usage data from that one-time offer, you'll know far more about willingness to pay than any estimate I can give you now, and that data should directly inform whether to add a recurring tier on top (Option A or D) rather than guessing at a subscription price upfront. Building the subscription first, before you know whether people convert at all, risks a lot of billing-infrastructure work for a hypothesis you haven't tested yet.

One practical note either way: whichever option you build, the fix I made to the discovery-board upgrade message today gives you a real, working entry point to point that "Upgrade" prompt at — right now it just displays text with nowhere to send the click. That's the natural next piece of code to write once you decide which option to pursue.
